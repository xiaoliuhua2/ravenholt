# 外部情报源：公开资产清单 / CT 日志 / 内网 IP 泄漏（通用，2026-09-24 乐信实证）

> 适用场景：拿到一个新 SRC 目标后，**在动手前**先做一轮 OSINT —— 它能一次性给出
> 「**资产面**（有多少域族、多少子域）」+「**自身泄露面**（内网 IP、内部设施）」，
> 而且几乎零请求、零风险。**这条流程收益远高于直接扫主域。**

## 1. ★★★ 公开资产清单源：GitHub 上的「SRC 爬虫」项目

**这是最容易忽视、收益最高的一类源。** 有一批公开仓库把**各厂商 SRC 目标的资产扫描结果**
整批提交到 GitHub（含域名 / 解析 IP / 开放端口 / Web 服务器 / 状态）。

### 1.1 已确认可用的仓库（覆盖数十家目标）

| 仓库 | 内容 | 备注 |
|---|---|---|
| **`LangziFun/BuTian_Spider`** | `补天爬虫/其他途径获取SRC/<来源>/<厂商>/<domain>.txt` | ★ 主源，`jiaya` 一目录下即 **29 家目标**（360 / oppo / 小米 / 完美世界 / 宜信 / 乐信 …） |
| **`hifuck/Security_Code`** | 同一批文件的副本（`Spider/BuTian.NET/CODE/…`、`漏扫系列/…/dir/<厂商>/`） | 交叉验证同一份数据 |
| **`LangziFun/LangSrcCurise`** | `initialize/domains.list`（一行一个根域） | ★ **先拉这个**：一次拿到目标**全部域族根域名** |

### 1.2 文件格式（制表符分隔）

```
域名	解析IP	开放端口	WEB服务器	网站状态
shop.example.com	119.29.49.163	80,443	Tengine	80:正常访问
internal.example.com	10.1.52.60	-	端口未开放	端口未开放
```

### 1.3 使用要点（踩过的坑）

1. **路径含中文 ⇒ 必须 URL 编码**才能 curl（`%E4%B9%90%E4%BF%A1` = 「乐信」）。
   或者改用 `mcp__github__get_file_contents`（MCP 自动处理）。
2. **一个厂商常有多个域族目录** —— 亲例一家厂商就有 **5 个**不同后缀的域族
  （`主品牌.com` / `集团名.com` / 若干收购品牌域名），**只拉一个会漏掉大半**。
   先列目录再逐个拉。★ 通用规律：**先查商标/收购历史，把域族列全再开工**。
3. ★★ **它是第三方扫描结果，不是厂商泄露** ⇒ **本身不能报成目标漏洞**（见 §5 纪律）。
   但它是**合法侦察输入**。
4. ★ **必须验证时效性**：清单可能几年前抓的。**IP 会大规模迁移**
   （乐信实测：历史腾讯云 `119.29.x`/`115.159.x`/`123.206.x` → 现在华为云 `81.x`/`113.x`/`121.x`）。
   验证方法见 §3。

## 2. ★★ 证书透明度日志（crt.sh）—— 找**未出现在清单里**的子域

```
https://crt.sh/?q=%25.<domain>&output=json        # %25 = 百分号，即 *.domain
```

对 `lexin.com` 一次拿到 11 个子域，其中 **清单里完全没有**的有：
`u-learning.lexin.com`（学习平台）· `shvpn` / `sslvpn` / `whvpn`（**三个 VPN 入口**，暗示多地办公）·
`co-doc`（文档系统）· `autodiscover` / `auaodiscover`（Exchange）。

### 要点

- 返回 JSON 里 `name_value` 字段**可能含多行**（`\n` 分隔）⇒ 必须 split 后再去重。
- ★ **`*.domain` 通配符条目必须单独看**：它解释"某子域为何不在 CT 日志里"。
  乐信亲例：`datashare.lexin.com` **不在** CT 记录中 ⇒ 被 **`*.lexin.com` 通配符证书**覆盖。
  **别把"CT 里没有"读成"这个域名不存在"。**
- crt.sh 偶发返回非 JSON（限流/超时）⇒ 解析要 try/except，并记录 raw 大小判断。

## 3. ★★★ 内网 IP 泄漏（公网 DNS 泄漏 RFC1918）——**判断"是否活配置"的关键技巧**

### 3.1 现象
某些**内网系统**的域名被签发到**公网 DNS**，解析结果是 RFC1918 地址（`10.x` / `172.16-31.x` / `192.168.x`）。
任何人在公网做一次 DNS 查询即可拿到**内网地址与主机命名体系**（`gitlab` / `jenkins` / `zabbix` / `yum` …）。

### 3.2 ★★ 时效性判定法（本轮固化的技巧）
清单给的是**历史值**，要判它是不是"还在"，**只做 DNS 解析**（零请求、零风险），然后比对：

| 情况 | 判读 |
|---|---|
| 当前值 == 历史值 | 记录**未变**，仍有效 |
| 当前值 ≠ 历史值（尤其是**公网 ↔ 内网 互换**） | ★★ **配置仍在维护 ⇒ 活配置**，价值更高 |
| NXDOMAIN | 已下线 |
| 解析到**保留地址**（`253.x` / `249.x` 等） | ★ 疑似**蜜罐/防护/解析失败**，标注为低置信度，别当事实 |

**乐信亲例**：`manage.dszc-amc.com` 历史是公网 `123.207.3.80`，**现在是 `10.9.9.9`** ——
公网→内网的变更**证明配置是活的**，不是陈旧缓存。最终确认 **8 个域名当前解析到内网**，跨 3 个域族。

### 3.3 定级口径（别写高）
- 这是**信息泄露 / 配置问题**，按 `03` 通常**低危**（或更低）。
- 泄漏的是**拓扑信息**，**不直接给访问权**；其价值取决于攻击者是否已在可达内网的某处。
- ❌ **不要写**「可打内网」「内网可达」—— 除非另有实测。
- ★ 同类可对照案例：理想汽车（09-21）**40 个**域名解析到 RFC1918，属同一族发现。

## 5. ★ 纪律与边界（写死）

1. **这些清单是第三方公开的扫描结果 ⇒ 不能报成目标的漏洞。**
   可报的只有**目标自己配置导致的**部分（如 §3 的内网 IP —— DNS 记录是目标自己的配置）。
2. **DNS 解析零风险，可以放心做**；但**别对清单里的资产做批量探活**就把规模拉过红线
   （单发、低量 ≤10/分、非破坏）。大批量前先问是否立案。
3. **看到 VPN / 邮件 / 学习平台 / GitLab / Jenkins 这类设施域名 ⇒ 只登记，不尝试登录。**
   验证凭证是否有效 = 未授权访问，属红线。
4. **同 IP ≠ 同一应用**：必须按 Host 实测。亲例：`datashare.lexin.com` 与 `www.lexin.com`
   同 IP，但换域名访问同一路径返回的是**另一个应用**（200 + 另一个 HTML / 302）⇒ **按 Host 分流**。
   ★ 这条**否定结论**同样有价值 —— 避免"多域名入口面"的误判。
5. 公开清单里的**解析到保留地址**的条目（`253.x`/`249.x`）标注为**低置信度**，不当事实引用。

## 6. 一次完整流程（可直接照做）

```
1) LangSrcCurise/initialize/domains.list        → 拿到目标全部根域（一次拿全，别漏域族）
2) BuTian_Spider 的 <厂商> 目录                  → 列目录，逐个拉全部域族清单
3) 汇总所有条目：域族 / 子域 / 历史IP / 端口 / 状态
4) DNS 复验全部条目（零请求）                     → 标出 ① 仍活 ② IP 变更（=活配置） ③ 内网 ④ NXDOMAIN
5) crt.sh 查各根域                               → 补清单里没有的子域；★ 单独看通配符条目
6) GitHub 内部代号 / com.<corp> / @corp.com 检索  → 判有无源码/凭证泄露
7) Maven Central 查 groupId                      → 有制品则下 jar 做静态分析
8) 同 IP 域名做 Host 分流实测（少量只读 GET）      → 判是否多域名同应用
9) 产出：资产总表 + 泄露面清单 + 时效性标注 + 定级（信息泄露类通常低危）
```
