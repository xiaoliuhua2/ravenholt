# 多字段核验接口的字段级 oracle → 枚举还原证件号

适用：站上有一类「核验」接口，body 吃 **号码 + 姓名 + 证件号**，返回「是否匹配」。  
本形态的洞点不在核验本身，而在**它把每个字段的对错分开告诉你**。

## 一、认什么

发一次错值，看返回文案是否**按字段拆分**：

| 返回                        | 含义           |
| ------------------------- | ------------ |
| `姓名不一致`                   | 姓名错，**证件号对** |
| `证件号码不一致`                 | 证件号错         |
| `姓名不一致、证件号码不一致`           | 两个都错         |
| `操作成功` / `isSuccess:true` | 全对           |

只要出现**字段级差异文案**（哪怕只是把「哪个字段错」拆开），接口就退化成两个独立 oracle。  
反过来，若失败永远是同一句「核验失败 / 信息有误」，**形态不成立**，别硬打。

## 二、为什么能还原完整证件号

身份证号 = `前6位(行政区划) + 8位(出生日期) + 3位(顺序) + 1位(校验位)`。

- **前 6 位 + 后 4 位**通常有现成来源：同站"脱敏展示"接口（前 6 后 4）、卡 BIN、社保/学籍等旁路。
- 一旦拿到前 6 后 4，**未知只剩中间 8 位**，而它只能是一个**合法日期** ⇒ 空间 ≈ 46,000（1900–2026）。
- 固定一个**必然错误**的姓名去枚证件号：报「姓名不一致」= 该证件号对了；报「…、证件号码不一致」= 错。  
  **不需要知道姓名**（字段各自独立判定），所以姓名不进枚举的乘法项。
- 反过来，固定正确的证件号、逐个换常见姓名，可把真实姓名也定出来。

## 三、打法（三步）

1. **摸 oracle**：拿一个已知全对的样本（自己的号/自己的证件）打一发，确认返回成功；  
   再分别改姓名、改证件号各打一发，确认返回**分成两句**。三步定形态。
2. **锚定未知段**：从同站脱敏接口或旁路拿到前 6 后 4（或卡号 BIN/尾号），把空间压到可枚举量级。
3. **最小枚举证明**：**只打 3 枪**——正解前一日 / 正解 / 正解后一日，证明只有正解那一枪文案变短。  
   报告里写清理论空间（≈4.6 万）与按此可还原，**不要真跑批量枚举**。

## 四、假点（别当洞）

- 返回永远是同一句统一失败文案 → 无字段差异，形态不成立。
- 核验口要求登录态、或要求短信验证码 / 图形码先过 → 有前置闸，按 `dig-scope` §4.2.2 另判。
- 证件号整体未知、且**没有任何锚点片段** → 空间 10^18，不可枚。
- 只回「是否匹配」但**不区分是哪个字段错** → 只能做二值判定，无法拆出单字段（除非你已完全掌握其中一个字段）。
- 把「接口 200 有 JSON」当穿透；把「能核验自己」当洞。

## 五、红线

- 只做**差分证明**（3 枪量级），禁止批量枚举、禁止对他人做全量还原。
- 命中即**高危**（`03-vuln-report-format.md` 高危第一档「对得上人」），未到严重。

## 七、实测（陕西电信小程序，2026-09-15）

`/elecWx/multi/custInfoManage/certificateValid`（前端名 `checkIdentity`），body  
`{serviceNbr, latnId, prodType, certiName, certiNbr, certiType}`，**无登录态可调**。

```
{1770921****, 贯禹, 510802****0924****} → {"code":200,"isSuccess":true}
{1770921****, 张三, 510802****0924****} → 姓名不一致
{1770921****, 贯禹, 510802****0924****} → 证件号码不一致
{1770921****, 测试, 510802****0924****} → 姓名不一致、证件号码不一致
{1770921****, 测试, 510802****0924****} → 姓名不一致        ← ★ 证件号对了
{1770921****, 测试, 510802****0924****} → 姓名不一致、证件号码不一致
```

前 6 后 4 由同站未授权接口 `custInfoManage/getCustInfoByCustNum` 提供（脱敏形态 510802\*\*\*\*0924\*\*\*\*），  
中间 8 位即出生日期 ⇒ 完整证件号可被还原。已落高危报告。

## 八、取证：加密通道下怎么留"完整请求包"

这类接口往往在网关加密通道里（body 是密文、响应也加密）。**抓包存下来的只有明文参数与响应，  
密文和 `access` 类时效头是存不住也复现不了的**——直接把抓包内容贴进报告会缺东西。

正确做法：**用 PoC 的加密函数现场重算一对密文**，贴进报告时标明「密文为实时生成」。

- 明文 JSON 与明文 hex **恒定**，可逐字对照，是报告的主体证据。
- 密文（`encryptedData` / `reqAccess`）与 `access` **每次必变**（前者含 SM2 随机数，  
  后者含毫秒时间戳），报告里注明这点即可，不算"省略"。
- **不要试图本地解密 `reqAccess` 来自证**：请求公钥的对应私钥在服务端，前端只硬编码公钥，  
  本地解不开是正常的（踩过坑，会误判成链路坏了）。验证走**结构自洽**：
  - `reqAccess == encryptedData`（两者恒等）
  - `len(密文hex) == 2 × (96 + len(明文hex))`（SM2 C1C3C4 布局：C1=64B 无 04 前缀）
  - `access` Base64 解码 == 128 字节（RSA-1024 单块）
- 生成脚本与报告放同一目录（`复现/gen_cert_packets.py`），需要新密文时直接跑。  
  跑完**把每段密文回填后要脚本化校验一遍**（`assert v in md`），防止手抄 hex 出错。

## 九、★ 参数语义「双轨判定法」：源码枚举 × 实测差分（2026-09-16 实证）

交付文档常要回答「这个参数有哪些取值、每个取值什么意思」。**只读源码会写错结论**——
源码只反映「前端会传什么」，不反映「服务端消费什么」。必须两条轨都跑，且以实测为准。

**轨一（源码枚举）**：全量扫 `.js`，对每个参数穷举 `key:\s*"值"` 的字面量，逐个挖上下文语义。
- **语义靠同段中文线索，不靠字面猜**：`console.log("有登录，用的是固话 || 宽带 ||异网")` 直接锤死
  `prodType` 的 `2`/`5`/`8`；`{latnName:"西安",latnId:"290"}` 直接给出地市对照表。
- **真值来源要追到服务端接口**：`prodType` 由 `validAndChangeProdType` 回填，不是前端编的。
- 字典型参数（`channel` 10 种）逐个 debug：`308`=线上埋点(`savePvUv`)、`307`=线下(`isOffline()`)、
  `wx`=微信授权登录、`01`=服务评价、`HB`=分享、`KFC20200324`=门店自提、`S100C10070`=优惠专区。

**轨二（实测差分）**：写脚本对每个参数的多个取值各发一枪，**比对响应是否逐字变化**。
- **判别口诀**：改值后响应**逐字相同** ⇒ 服务端**不消费**（纯前端分支/埋点）；
  出现**独立报错文案** ⇒ 服务端**有专属校验分支**。
- **独立报错文案是最强证据**：`latnId=""` → `地市编码为空`、
  `accNbr=""` → `查询号码为空`——比 HTTP 码和通用错误信息可信得多。
- **通用报错（如"查询用户信息失败"）不足以定性**：它可能是格式错、匹配错、或内部异常，
  必须再设计**交叉对照**才能区分。

### ★★ 本案最大的教训：`custCard` 被误判了整整一轮

旧结论（**错**）：`custCard` 三处调用点全传空且传空也返回数据 ⇒ **服务端不校验这一项**。

实测 8 例后的真相：

| `accNbr` | `custCard` | 结果 |
|---|---|---|
| 125（贯*） | `""` | ✅ 成功 |
| 125（贯*） | 贯*真实证件号 | ✅ 成功 ← **正配** |
| 125（贯*） | 他人证件号 | ❌ 拒 |
| 126（魏*） | 贯*证件号 | ❌ 拒 ← **反向交叉** |
| 125（贯*） | 真号**仅改末位 1 位** | ❌ 拒 |

⇒ `custCard` 是**「与机主证件号逐字符一致性校验」**，且**允许为空（空=跳过）**。

**为什么交叉对照是必需的**：只有「匹配→成功 / 不匹配→失败」的**双向**数据，才能把
「一致性校验」与「独立查询键」「格式校验」三者区分开。单发一枪永远分不清。

**这个修正改变了漏洞定性（加强而非削弱）**：
- 旧：「服务端没实现校验」→ 责任在服务端缺失防护。
- 新：「服务端实现了校验，但**允许字段为空**，而前端**主动传空**」→
  **「有开关但默认关闭」**，且服务端 / 前端**两处均可举证**。

### ★ 副产品：把「查询接口」改造成「低成本 oracle」

同一接口填入「已知字段」即可变成校验器：`code=200` 为一致、`code=500 查询用户信息失败` 为不一致。
本案 `getCustInfoByCustNum` 填入 `custCard` 后即为**证件号一致性 oracle**，
可用来**交叉验证**由 `certificateValid` 爆破还原出的身份证号 —— 
核验类接口一次一问很慢，查询类接口可直接给二元结论。**报告里写清这条联动链。**

### 交付物形态

- `*_参数取值表.md`：**参数 | 源码取值 | 服务端是否消费 | 实测结论** 四列一张总表（放最前面）。
- 每个参数一节：源码原文（**逐字，含空格**）+ 实测表 + 判读。
- **必须附「对已有文档的修正清单」**：写清哪句旧结论错了、应改成什么——否则错误结论会随文档流传。
- 实测结果落盘 `.txt`（`param_diff_*.txt`），与文档同目录，供复核。

### 复现踩坑

- 差分脚本**不要改 PoC 本体**：在脚本里 `importlib` 加载 PoC，复用其 `_SM2`/`_RSA_C`/`rand32` 等对象，
  自己重拼 biz → `stringtohex` → SM2 加密 → 组装 headers/body。PoC 的 `build_request` 通常只暴露
  部分参数（如只有 `phone`/`desflag`），**不要硬塞 dict**，否则会误用。
- **文档校验要「两阶段」**：第一遍校验常常自己写错检查项（把只该出现在 A 文档的片段去 B 文档找）。
  第一遍 FAIL 要先分辨「文档错」还是「校验项错」，再改。
- **源码引用务必逐字**：`desFlag:t` 与 `desFlag: t` 差一个空格就 `in` 判假。
  写文档时从 dump 结果**直接复制**，别凭记忆重敲。

## ★★ 反面判据：「换参数值得到不同响应」**不等于**「参数被消费」（2026-10-03 实证）

**症状**：两个免登录接口看着像 oracle，据此写了「未授权枚举账号 + 未授权读他人密保问题」：

| 接口 | 表面现象 | 当时的推理（❌） |
|---|---|---|
| `POST user/is-exist {loginName}` | `admin`→92668751、`root`→3506402、`justForTest`→869612143 | "能拿到不同 userId ⇒ 是账号表 id ⇒ 可枚举账号" |
| `GET secret-problem/list?userId=N` | N=2/3/100/92668751 各返回**不同**的 3 条密保题 | "结果随 N 变化 ⇒ 参数被真实消费 ⇒ 读到了该账号的密保" |

**复验后的真相**（两步，都只读）：

**① 用「确定不存在」的输入做对照**
```
user/is-exist {loginName:"zzz_nosuchuser_xyz"}  → 1808789422  （连发 5 次全同）
user/is-exist {loginName:"qqqzzz_nonexist_9x"}  → 157386110   （3 次全同）
user/is-exist {loginName:"admin"}               → 92668751    （稳定）
```
⇒ **连永不存在的用户名也返回稳定的"userId"**；且 `zzz_nouser_xyz`→1795694603 与
`zzz_nosuchuser_xyz`→1808789422 **仅差 4 个字符结果雪崩** ⇒ 这是 **loginName 的哈希派生值**，
**不是数据库主键**。（衍生：所谓「后门账号 justForTest」也就**没有证据**了。）

**② 找返回值的**生成规律**（而不是"是否变化"）**
```
secret-problem/list?userId=N → ids
N=0 → [1,2,4]   N=2 → [3,4,6]   N=3 → [4,5,7]   N=4 → [5,6,8]
N=100 → [23,24,26]   N=1000000 → [15,16,18]   N=123456789 → [2,3,5]
```
⇒ 完全符合 **`N % 26` 起取 {0,+1,+3} 三个偏移** = **题池共 26 条、按 N 取模选 3 条**。
⇒ 返回**与"账号是否存在/是否配置过"完全无关**；"不同 userId 不同密保"只是**取模结果恰好相邻**。

**判据（可直接套用）**：
1. **必答一题**：「目标上**没有**这个账号/资源时，它回什么？」
   —— 答不出，这个判据就**没有判别力**，**不能下结论**。
2. **必看生成规律**：把返回值当**参数的函数**去拟合（取模 / 哈希 / 区间 / 递增），
   **别只看"变没变"**。相邻输入的输出相邻 ⇒ 强烈提示**取模/切片**类派生。
3. **稳定 ≠ 真实**：**稳定**只能排除"随机/自增"，**不能**证明"对应真实实体"。
   判真实性要**换维度**（换一个必然不存在的输入，看是否同样稳定）。
4. **同一错误码家族要当"同一类响应"**：本例 `user/is-exist` 与 `secret-problem/list` 都属
   「口令找回免登录族」，**整族可能都不查库**（返回模板/派生值）⇒ 一句话笼统口径「免登录接口面过宽」
   是对的，**具体到"账号数据泄露"就是越狱**。

**连带纪律（报告卫生）**：撤销结论时**要在原文就地标注**（~~旧结论~~ + ✅/❌ + 新判据），
并同步**所有引用该结论的文档**（本例两份报告 + 速览表的定级一并从"中危"降为"信息级"）。
